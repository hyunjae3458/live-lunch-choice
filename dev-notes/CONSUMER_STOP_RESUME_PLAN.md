# Consumer 중단·재개 실험 인계

## 사용자 요청과 목적
사용자는 정상 Kafka 브로커 송수신을 직접 확인했다고 보고했다. 다음에는 CLI 대화에서 리스너 제어 기능을 구현하고 실제 실험까지 진행한다. CLI는 사용자의 구현을 지원하고 요청받은 실험용 코드 작성·검증·실행을 수행하며 결과를 반드시 기록한다. 다른 Kafka/Redis 기능까지 자동 확장하지 않는다.

목적은 Producer와 Consumer의 역할 및 실행 의존성 분리를 확인하는 것이다. Consumer가 중단돼도 투표 접수와 Kafka 발행이 계속되고, 미소비 이벤트가 보관되며 재개 후 커밋된 소비 위치부터 따라잡는지 관찰한다. 이는 정상적인 Consumer 중단·재개 실험이며 브로커 장애, 처리 중 강제 종료, 정확히 한 번 처리 또는 영속 발행 복구를 증명하지 않는다.

## 구현 범위
- 기존 KafkaListener id=vote-log-listener, groupId=vote-log-group 및 토픽 vote-created 유지. 최신 코드를 먼저 확인한다.
- KafkaListenerEndpointRegistry.getListenerContainer("vote-log-listener")로 컨테이너를 찾아 stop()/start()하는 작은 로컬 실험용 Controller를 준비한다. 컨테이너가 없을 때의 오류도 처리한다.
- 제안 API: POST /api/local/kafka/consumer/stop, POST /api/local/kafka/consumer/start. 정상 응답 204. 필요하면 running 상태를 읽는 간단한 조회를 추가해도 된다.
- @Profile("local")로 로컬 실습에서만 활성화하고 사용자의 기존 프로필 설정과 충돌하지 않게 한다. 환경변수 SPRING_PROFILES_ACTIVE=local로 실행 가능. 설정 파일은 YAML, 설명과 새 예제는 명시적 Java 타입 사용.
- Consumer 메서드 본문만 비우거나 주석 처리하지 않는다. 그렇게 하면 읽기·정상 반환·offset 커밋이 계속될 수 있다.
- API/Producer/브로커는 계속 유지하고 Consumer 컨테이너만 제어한다. H2 메모리 DB를 유지하도록 실험 중 앱 재시작을 피한다.
- 구현 확인에는 필요한 범위의 테스트를 사용하되 mock 기반 테스트를 실제 Kafka 실험 완료로 취급하지 않는다.

## 실험 전 확인
- 실제 실행 환경·현재 앱·브로커를 먼저 확인. dev-notes/KAFKA_COMMANDS.md의 lunch-kafka 및 localhost:9092는 기존 실습 값이며 현재 환경과 대조한다.
- 같은 그룹의 다른 Consumer가 대신 소비하지 않도록 해당 그룹 구성원을 확인한다. 무관한 프로세스를 종료하지 않는다.
- 정상 투표 한 건으로 송수신 및 커밋 완료를 확인하고 기준 offset/lag를 기록한다. 기준 lag=0을 기다린다.
- 기존 후보 ID를 확인하고 실험별로 새 userId를 사용한다. 3건은 순차 요청하며 별도 트래픽이 없는 상태로 진행한다.
- 토픽 삭제, offset reset, DB 초기화 및 기존 데이터 정리는 하지 않는다.

## 실행 순서와 관측
1. 기준 시각/HTTP 응답/같은 eventId의 발행·수신 로그와 그룹 CURRENT-OFFSET, LOG-END-OFFSET, LAG를 기록한다.
2. stop API 호출 후 완료 응답 및 리스너 종료 상태를 확인한다. 중단 이전 처리 중이던 레코드와 이후 신규 레코드를 구분한다.
3. 새 사용자 세 명으로 투표를 순차 등록한다. 각 201, DB 저장, eventId/voteId와 PUBLISH_SUCCEEDED를 확인한다. 이 세 이벤트의 CONSUMER_RECEIVED는 중단 동안 없어야 한다.
4. 그룹 조회 원본 출력을 저장한다. 기준 커밋 위치 유지, 끝 위치 증가, 미소비 lag 증가를 확인한다. 단순한 비트랜잭션 단일 파티션 실험에서 다른 트래픽이 없으면 lag 3을 기대하지만 실제 값과 조건을 먼저 기록한다. 그룹에 활성 구성원이 없다는 안내는 중단 중 정상일 수 있다.
5. start API 호출 후 실제 그룹 참여/파티션 할당과 수신을 기다린다. 204 자체는 처리 완료가 아니다.
6. 동일한 eventId 세 건이 해당 파티션의 offset 오름차순으로 수신되는지, 최종 커밋 위치가 끝 위치를 따라잡고 lag=0이 되는지 확인한다.
7. 리스너가 최종 실행 중인 상태인지 확인하고 마무리한다. 실패해도 가능한 범위에서 원래 리스너 상태를 복구하고 복구 결과를 기록한다.

## 결과 기록: 반드시 수행
- dev-notes/CONSUMER_STOP_RESUME_RESULT.md에 실행 일시(KST), 앱/브로커/토픽/그룹/파티션/복제 계수, 실제 실행 명령과 HTTP 요청을 남긴다. 명령은 복사 가능한 한 줄로 작성한다.
- 기준/중단 후 3건 발행/재개 후의 실제 CURRENT-OFFSET, LOG-END-OFFSET, LAG를 표로 기록한다. 예상값과 관측값을 분리하며 예시 숫자를 결과로 쓰지 않는다.
- eventId별 voteId, 발행 성공 로그, Consumer 수신 로그 및 topic/partition/offset을 연결한다. Consumer 수신은 집계 완료나 offset 커밋 성공 자체와 다름을 유지한다.
- DB 투표 저장 증거, HTTP 상태, 중단 중 미수신 관찰 구간, 최종 리스너 상태를 기록한다. 로그나 출력이 없다면 미확인으로 적는다.
- 사용자 직접 관찰 보고와 CLI가 도구로 직접 검증한 결과를 구분한다. 오류/예상과 다른 결과/해결 과정/남은 한계도 기록한다.
- dev-notes/PROGRESS.md에 구현 파일, 테스트 결과, 실제 실험 결과 요약 및 결과 문서 링크를 추가하고 상단 현재 상태를 갱신한다.
- 실행이 막히면 원인과 미실행 항목을 남기고 완료로 표시하지 않는다. 문서 준비 상태를 실험 성공으로 바꾸지 않는다.
- 마무리 시 접수와 소비의 분리, 보관된 이벤트를 이어 읽는 동작, 소비 후에도 이벤트가 보관되는 점을 관측 결과에 연결해 한국어로 설명한다.
