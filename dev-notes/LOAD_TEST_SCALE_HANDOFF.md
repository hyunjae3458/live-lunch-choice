# 단계별 부하 비교 실행 인계

## 목적과 현재 증거
사용자는 소규모 결과를 검토하고 관측기 재검증 → 관람자 증가 → 투표량 증가 순서의 다음 실험을 CLI에 요청했다. 이전 '대규모 조건 논의 대기'는 아래 한정된 실행 범위로 갱신한다. 수천 연결/자동 포화 시험/제품 최적화는 포함하지 않는다.
기존 관람자10/1req/s/30초 결과는 두 모드 최종1030표 일치. polling은 투표 API 지연·본문량이 작고 realtime은 누적 목표치 관측이 빨랐다. realtime의 부하 중 자원·lag는 관측기 오류로 미측정이므로 기존 결과를 자원 효율 비교에 쓰지 않는다.

## 먼저 읽기
AGENTS.md, PROGRESS.md, LOAD_TEST_PLAN.md, LOAD_TEST_PILOT_RESULT.md, load-tests/README.md와 실제 스크립트를 읽는다. 최신 사용자 모드 전환 선호를 유지한다: polling 결과를 먼저 보여주고 사용자 환경변수 전환 확인을 받은 후 realtime 실행. 이 절차를 자동화로 임의 변경하지 않는다. 별도 승인 없는 기존 앱/DB/인프라 종료·초기화 금지.

## 1단계: 관측기 재검증
- 새 실험 데이터 기준으로 각 모드 관람자10/투표1req/s/측정30초를 실행한다. 원본 과거 결과와 실패 summary는 보존한다.
- 수정한 호스트 Admin 조회와 자원 수집이 실제 부하 구간에서 주기적으로 동작하는지 확인한다. 샘플 타임스탬프/수집 간격/누락·오류 수를 기록한다. lag 명령 대기가 자원 수집을 막지 않도록 타임아웃·관측 작업 분리를 점검한다.
- API 성공률, DB 후보별 변화량, realtime Redis 일치, 모든 관람자의 최종값, 부하 후 lag0 확인. polling은 Kafka/Redis를 쓰지 않음을 유지.
- 실제 요청률이 목표와 맞는지, 발생기 지연/미발행 요청/클라이언트 오류가 없는지 검증한다. 실패하면 측정 도구만 보완하고 이 단계부터 재검증한다. 유효한 시계열 없이 다음 단계로 넘어가지 않는다.

## 2단계: 관람자 증가
- 앱1개, 투표1req/s 고정. 관람자10 → 50 → 100명.
- 모드별 각 조건 측정60초, 유효 실행3회. 동일 후보4/초기1000표400·300·200·100/동일 인덱스와 자원 설정.
- polling은 응답 완료 후2초 대기, realtime은 실제 SSE 연결·메시지 수신. 관람자 접속 시각은 두 모드에 같은 분포를 적용하고 동시 시작인지 분산인지 기록한다.

## 3단계: 투표량 증가
- 관람자100명 고정, 투표1 → 5 → 10req/s, 각 모드60초/3회.
- 100명/1req/s는 2단계와 동일 조건·설정이면 결과 재사용해 불필요하게 반복하지 않는다.
- 명확한 요청 도착률로 발생시키고 성공한 투표만 정확성 기준으로 사용한다. run별 고유 userId 및 미리 정한 동일 후보 배분 사용. 단일 동기 writer가 느려져 목표 요청률을 못 만들면 서버 처리 한계와 구분하고 발생기를 수정한다.

## 공정성과 데이터
- 각 반복마다 동일 초기 상태를 준비한다. 기존 결과는 보존하고 실험 전용 소유 마커가 확인된 DB/키/토픽/컨테이너만 전용 준비 도구로 재설정하거나 새로 생성한다. 실행 중 앱/이전 Consumer가 데이터에 쓰지 않는지 먼저 확인한다. 사용자 live_lunch_choice/기존9092·6379와 격리 유지.
- 초기 DB/Redis 기준값 검증. 시드 직접 입력과 합성 처리 기록의 한계, 이전 이벤트 재발행 금지 유지. 자동 초기화 제품 API를 만들지 않는다.
- 읽기뿐 아니라 쓰기/Producer 워밍업도 두 모드에 동일 조건으로 수행하고 측정에서 제외한다. 워밍업 투표는 삭제 후 옛 이벤트가 남는 식으로 처리하지 말고 별도 사용자ID로 수행하고 집계 완료 후 새 기준값으로 기록한다. 모드별 시작 기준은 동일하게 맞춘다.
- 자원 설정/실행 순서/공유 PostgreSQL/기존 앱 경쟁/추가 Kafka·Redis 비용 명시. 순차 모드 실행의 시간대 편향은 한계로 기록한다.
- JSON 필드 차이/헤더·SSE 프레임 포함 여부 및 응답 완료 기반 Polling 주기를 유지·명시한다. 성능을 좋게 보이게 하려고 측정 중 주기/집계/전송 정책을 변경하지 않는다.
- SSE60초 타임아웃과 재접속 처리/연결 공백을 측정한다. 조용히 타임아웃을 늘려 재접속 비용을 숨기지 않는다.

## 측정 및 분석
- 투표·조회 API별 시도/성공/실패/실제 RPS, p50/p95/p99. 3회별 결과와 편차를 보여주고 p95들을 합쳐 전체 p95라고 부르지 않는다.
- 누적 목표치 관측 지연과 최종 수렴 시간. 고부하에서 누적 득표로 개별 이벤트 순서를 보장할 수 없으므로 개별 투표 지연으로 표기하지 않는다. 동일 투표를 관람자별 관측한 값의 상관성도 명시한다.
- DB/Redis 후보별 최종 정확성, Kafka lag 시계열/부하 후 해소, SSE 연결 성공·수신 수·재접속·최종 관람자 수.
- 앱/DB/Kafka/Redis/발생기 CPU·메모리와 가능한 쿼리·네트워크 지표. 공유 PostgreSQL 전체 CPU를 해당 실험 DB 단독 비용으로 해석하지 않는다. 미수집 지표는 추정해 채우지 않는다.
- 현재 thread-per-viewer 도구는 최대100명까지만 사용. 발생기 CPU/스레드/FD/요청 스케줄 지연이 병목이면 서버 용량 결론을 보류한다.

## 단계 중단 기준
- 최종 집계 불일치, OOM/스왑 급증, HTTP 실패율1% 이상, 투표p95 1초 초과, 부하 종료30초 내 lag 미해소 또는 관측기 실패 시 다음 부하 증가를 중단하고 원인을 기록한다.
- 이전 도구의 '오류3건 중단'과 새 기준이 충돌하면 명시적으로 정리하고 실제 사용 기준을 기록한다. 무조건 다음 단계까지 밀어붙이지 않는다.
- 각 실행은 제한 시간으로 끝내며 실패를 무한 재시도하지 않는다. 기능/측정 결함 수정은 가능하나 서버 성능 최적화는 baseline 결과를 보존한 뒤 별도 논의한다.
