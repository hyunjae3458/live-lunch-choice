# 최신 사용자 실행 정책 (2026-10-19)
발생률·스케줄 지연 등 경미한 기준 미달은 기록하고 비교를 계속한다. 기존 SLO 평가를 성공으로 바꾸지는 않는다. OOM·장시간 성공응답 없음·최종 데이터 불일치 등 critical에서 중단한다. 아래 과거 환경경고 중단 지시보다 최신 사용자 결정이 우선한다. 현재 실행 결과는 CAPACITY_RESULT/PROGRESS/CLI_HANDOFF의 최신 기록을 따른다.

# 새 부하 실험: DB·SSE 대 Kafka·Redis·SSE

## 사용자 결정과 목적
기존 polling/realtime 부하 결과는 사용자가 원하는 처리 용량 비교에 답하지 못해 폐기한다. 여기서 폐기는 신규 성능 주장·회고의 비교 근거에서 제외한다는 뜻이다. 원본 파일/실험 데이터 삭제를 수행하지 않으며 이전 수치를 새 결과에 섞지 않는다.

질문: 동일한 실시간 랭킹 요구를 제공할 때 누적 데이터와 요청량이 증가하면, 어떤 구조가 어느 부하까지 오류와 큰 갱신 지연 없이 유지되는가? Kafka·Redis의 승리를 전제로 하지 않는다. 둘 다 한계 미도달이면 그 사실을 보고한다.

현재 상태: 설계 및 CLI 인계만 완료. 새 프로필/측정기 미구현, 새 부하 미실행. 데스크톱은 방향/결과 분석, CLI는 구현/검증/실행 역할을 유지한다.

## 구현할 비교 대상
- A db-sse: 동일 투표 검증과 PostgreSQL 저장 → 커밋 후 로컬 알림 처리 → DB GROUP BY 집계 → SSE 전체 랭킹 전송. Kafka/Redis 사용 없음.
- B realtime: 동일 PostgreSQL 저장 → 커밋 후 Kafka → Redis Lua 집계 → Pub/Sub → Redis 랭킹 조회 → SSE 전체 랭킹 전송.
- 제품 polling은 유지하지만 이번 주요 비교에서 제외한다. 공통 SSE 전송부/결과 공급자 정도만 분리하고 대규모 리팩터링은 하지 않는다.
- A가 단순히 HTTP 스레드에서 모든 전송을 기다려 불리해지는 비교를 피한다. A 커밋 후 로컬 알림은 유한 큐·고정 worker를 가진 별도 executor에 넘긴다. 큐 용량/worker 수를 고정·공개하고 queue wait/depth/rejection을 측정한다. 무한 큐·작업 조용한 폐기 금지. 큐 초과로 DB 저장 후 알림 실패한 건도 실패로 기록한다. 이 로컬 큐는 영속성/장애 복구 보장이 없으며 Kafka와 같다고 설명하지 않는다.
- DB 저장/트랜잭션/인덱스/JVM/커넥션 풀/로그 수준은 양쪽 동일. 집계는 커밋 이후 최신 커밋을 볼 수 있는 별도 읽기 트랜잭션으로 수행하고 롤백 이벤트 미전송을 검증한다.
- 한 알림에 랭킹 한 번 조회 후 모든 연결에 전송. 관람자마다 DB 집계하지 않는다. 양쪽 동일 전체 스냅샷, candidateId/voteCount만, 동일 SSE 이벤트명. 후보 이름은 측정 시작 전 조회한다. 순위 동점 차이는 명시하고 정확성은 후보별 점수로 검증한다.
- 양쪽 기본 전송 정책은 집계 알림마다 전송. 한쪽만 debounce/batch/cache/누락으로 비용을 줄이지 않는다. 실제 알림/조회/전송 수를 기록하여 Pub/Sub 누락이나 중복 스냅샷을 구분한다.
- SSE 연결 수, 연결 도착 분산, timeout/재연결 정책 동일. 처리 용량 본 실험에서는 timeout을 워밍업+측정+drain보다 길게 두어 의도적 60초 재연결을 제거한다. 실제 끊김/재연결은 숨기지 않는다. 재접속 성능은 별도 실험이며 본 범위에서 자동 추가하지 않는다.
- 새 프로필 검증/모드 API/설정은 기존 계약과 충돌하지 않도록 추가하고 YAML 사용. 일반 polling/realtime 회귀 확인.

## 먼저 관측기와 격리 환경을 준비
- 기존 실제 서비스와 데이터는 보존한다. 새 run ID, 실험 전용 PostgreSQL 컨테이너/DB, Kafka/Redis 컨테이너/볼륨/포트 사용. 기존 공유 PostgreSQL로 CPU 귀속을 추정하지 않는다.
- 동일 노트북에서는 물리 자원 경쟁이 남는다. 가능하면 부하 발생기를 별도 호스트에 두되 별도 호스트가 없으면 로컬 한계로 명시한다. DB CPU/메모리, 앱 heap/CPU, Kafka/Redis 제한을 기록하고 양쪽 앱·DB 예산은 동일하게 둔다. 추가 인프라 비용도 별도 보고한다.
- 기존 Python 도구는 100명 상한과 thread-per-viewer 방식이다. 그대로 고부하 도구로 쓰지 않는다. 실제 SSE 파싱을 지원하는 비동기 I/O 발생기로 교체하거나 확장하고 발생기 자체 용량을 먼저 확인한다.
- 도착률은 응답에 따라 줄어드는 폐쇄 루프 대신 예약된 고정 도착률. 목표/실제 전송률, 미발행, in-flight, 스케줄 지연을 기록한다. 발생기 병목이면 서비스 한계로 판정하지 않는다.
- 준비 → JVM/쓰기/읽기 워밍업 → 관측기 정상 확인 → 측정 → 최대 60초 drain → DB/Redis/클라이언트 검증. 측정 전 seed와 워밍업까지 양쪽 동일한 기준값을 확인한다.
- 후보 4개, 균등 분포, 고유 userId, 동일 seed/요청 시퀀스. PostgreSQL 인덱스 및 ANALYZE 조건 동일. Redis seed는 DB 집계와 비교해 일치 확인. 반복마다 초기 상태 복구는 실험 도구에서만 수행한다.

## 두 단계 실험
### 1. 누적 데이터에 따른 집계 조회 비용 (원인 분리)
- 초기 투표 1만/10만/100만 건, 후보 수 동일.
- 투표 쓰기/SSE fanout 없이 DB 집계 결과 API와 Redis 랭킹 API에 같은 요청률을 준다. payload 동일, DB 후보 이름 join 등 추가 비용을 불필요하게 섞지 않는다.
- 10/50/100/200 req/s 단계로 진행하고 한계 주변만 재확인한다. 매 데이터 크기에 무조건 모든 조합을 실행할 필요는 없다.
- 조회 지연 p50/p95/p99, 완료 RPS, 오류/timeout, 집계 SQL 실행 수·시간, DB CPU/IO/버퍼, Redis CPU/명령 지연을 기록한다. SQL 횟수를 tup_returned로 대신하지 않는다.
- 이 실험은 매번 계산하는 집계와 미리 계산한 집계의 비교다. Sorted Set 자체나 Kafka의 단독 효과, DB 일반의 한계라고 주장하지 않는다. 쓰기를 제외한 진단 결과임을 명시한다.

### 2. 전체 실시간 경로 처리 용량 (주요 결론)
- A/B 모두 SSE, 관람자100명 고정으로 시작. 누적 데이터는 1만과 100만 건 두 조건을 사용해 데이터 크기에 따른 차이를 확인한다.
- 투표 도착률 10 → 25 → 50 → 100 → 200 req/s를 상한 있는 탐색으로 실행. 한 단계 30초 워밍업 + 180초 측정, 최대60초 drain. 실패 경계까지 가거나 환경/발생기 한계면 중단한다. 200에서도 둘 다 통과하면 그 이상을 검증했다고 하지 않는다.
- 탐색은 각1회, 마지막 통과/첫 실패 주변 조건을 각3회 재현. 순서는 A/B와 B/A 교차, 매번 동일 seed 복구. CPU throttling/GC/대기열을 함께 확인한다.
- 관람자 증가는 쓰기 부하 증가와 섞지 않는다. 양쪽이 통과한 동일한 투표률 하나에서 100 → 300 → 500명으로 별도 탐색하고 SSE 전송 병목을 구분한다. 발생기 검증 실패 시 증가 중단.
- 데이터 크기, 투표률, 관람자 수를 동시에 바꾸거나 한쪽 실패 뒤 다른 쪽만 유리한 설정으로 변경하지 않는다.

## 주요 지표와 임시 합격 기준
아래 수치는 운영 요구사항이라고 주장하지 않는 비교용 기준이다. 첫 본 측정 전에 고정해 결과 문서에 기록하고 결과를 보고 완화하지 않는다.
- 투표 접수: 목표 대비 실제 발생률 ≥99%, HTTP 성공률 ≥99.9%, API p95 ≤200ms / p99 ≤500ms.
- 결과 갱신: 요청 시작 → 목표 누적 득표 최초 관측 p95 ≤500ms / p99 ≤1초. 미관측은 통계에서 삭제하지 말고 별도 실패 수와 관측 종료시점까지의 하한으로 기록한다.
- 정확성: 최종 DB 투표 건수, HTTP 결과 불명확 건의 실제 커밋 여부, Redis 후보별 점수, 모든 클라이언트 최종값 대조. 누락/중복 집계 0. HTTP timeout을 DB 미저장으로 단정하지 않는다.
- 지속성: 마지막 60초에 queue/lag/최신성 지연이 계속 증가하면 API가 빨라도 지속 처리 통과로 보지 않는다. Kafka 최종 lag0만으로 합격 판정하지 않는다. DB 로컬 큐도 같은 기준으로 본다.
- drain: 투표 중지 후 60초 내 대기 작업 해소와 전원 최종 수렴. drain 성공만으로 부하 중 지연 기준 실패를 덮지 않는다.
- E2E는 기존 누적 목표치 관측으로 시작하되 개별 이벤트 완료 지연이라고 쓰지 않는다. 후보별 목표치가 순서와 다르게 충족될 수 있다. 정확한 단계 분석은 eventId로 커밋/발행확인/집계완료/알림 시각을 상관시키며 서버 계측은 양쪽 동일 정책 적용. 서버간 시간 동기화 및 계측 오버헤드 기록.
- CPU/RSS/GC/DB pool wait/SQL 시간, A worker queue, Kafka lag/발행 실패/consumer 처리률, Redis 명령 지연, SSE send 시간/접속/오류/전송량을 함께 수집. 순차 SSE send와 synchronized 잠금도 공통 병목 후보다.
- 요청 발생 지연, 미발행, 호스트 메모리 압박으로 목표 부하를 유지하지 못하면 해당 조건은 발생기/환경 제한으로 분류한다. 시스템 OOM/응답 불능이면 즉시 신규 부하 중단. SLO 실패는 삭제하지 않고 첫 실패 결과로 보존한다.

## 실행과 보고
- CLI는 위 범위의 새 프로필/관측기/격리 환경을 구현·기능 검증하고 소부하 동등성 확인 후 제한된 탐색/반복을 수행한다. 실험 환경의 모드 선택은 전용 설정으로 자동화해 반복마다 수동 .env 변경을 요구하지 않는다. 기존 사용자 설정은 변경하지 않는다. 종전 100명 상한/소규모 한정 계획은 이 새 계획 범위에서 대체한다.
- 각 단계 진행 요약을 사용자에게 알리고 환경 한계 또는 공정성 결함이면 원인과 미실행 범위를 남긴다. 무제한 자동 부하 상승 금지. 필요 없는 전체 조합으로 실행량을 늘리지 않는다.
- 의도적 sleep으로 A를 늦추거나 DB 인덱스를 제거하지 않는다. Kafka 효과를 만들기 위한 가짜 작업 추가 금지. 인프라 장애 주입/Outbox/초기화 API/다중 서버는 이번 범위 밖이다.
- 결과는 dev-notes/LOAD_TEST_CAPACITY_RESULT.md와 load-tests/results/capacity/<run-id>/에 저장. 환경·commit/diff·설정·실행 명령·seed·반복별 지표·마지막 통과/첫 실패·병목 근거·미검증 범위 명시.
- 반드시 구분: A와 B 전체 구조의 차이 / DB 재집계와 Redis 사전집계 차이 / Kafka 자체 효과는 아직 분리되지 않음. DB 쓰기가 먼저 막히면 양쪽 공통 한계, SSE가 먼저 막히면 전송부 한계, 관측된 다른 원인도 근거대로 보고.
- 기존 실험 결과로 빈칸을 채우지 않는다. 새 비교 준비만 했으면 실행 완료로 쓰지 않는다. 진행상황/설계결정/CLI 인계를 갱신한다.
