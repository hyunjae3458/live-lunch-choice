# 설계 결정 기록

기록일: 2026-10-15. 데스크톱 대화에서 합의한 결정과 선택 이유를 정리했다. 구현 완료를 의미하지 않는다. 이후 변경 시 기존 이유와 변경 이유를 보존한다.

## 1. 학습 방식과 범위
- 사용자는 동작 원리를 이해한 뒤 CLI와 구현·테스트한다. 이번에는 이해를 마친 Redis 랭킹 조회·Pub/Sub·SSE 구현과 검증을 CLI에 위임했다.
- 모든 희귀 장애를 예방하는 설계로 확대하지 않는다. 현재 Lua의 목적은 정상 Redis 실행 조건에서 경쟁 상태와 동일 eventId의 중복 집계를 방지하는 것이다.
- Redis 프로세스 장애, Lua 부분 실행 보상, 자동 재집계, Outbox, DLT, 대규모 부하 시험은 이번 범위 밖이다. Lua의 비롤백 한계는 이해하고 수용한다.

## 2. 집계 책임과 이름
- 사용자는 처음 기존 서비스에 메서드 추가를 제안했으나 향후 중복 처리·재집계 책임을 고려해 VoteAggregationService 분리에 동의했다.
- Redis 접근 클래스 이름은 사용자가 선택한 VoteRankingRedis를 유지한다. RedisUtil/VoteRankingRedisRepository로 바꾸지 않는다.
- 처리한 eventId를 Set에 저장하고 Lua에서 SISMEMBER → ZINCRBY → SADD를 실행한다. true는 순위 변동이 아니라 신규 이벤트를 집계했다는 의미이며 순위가 같아도 표 수 변경 알림을 보낸다.
- 같은 이벤트 재전달에는 같은 eventId를 유지한다. 처리 기록 TTL은 우선 두지 않는다. voteId가 같지만 eventId가 다르면 같은 이벤트로 판별하지 않는 현 범위를 유지한다.

## 3. Redis 순서를 유지하는 랭킹 조회 — 사용자 제안 채택
- 이전 예제의 Redis → HashMap → DB 후보 전체 조회 → Java 재정렬 방식은 적용하지 않는다.
- Sorted Set을 점수 내림차순으로 조회하고, 조회 순서대로 응답 DTO를 List에 담아 반환한다. DTO 필드는 candidateId, voteCount이며 이름은 포함하지 않는다.
- Redis 랭킹 경로에서는 후보 이름을 위한 DB 접근과 Java 재정렬을 하지 않는다. Sorted Set의 순위 조회 기능을 실제로 활용한다.
- 프론트는 기존 후보 목록 API에서 전체 후보 ID·이름을 가져온다. 랭킹 목록 순서를 유지해 표시하고, 목록에 없는 후보는 0표로 뒤에 표시한다. 각 SSE 메시지는 전체 최신 랭킹 스냅샷이므로 이전 값에 덧셈하지 않고 새 목록 기준으로 교체한다.
- 이번 백엔드 구현에 완성형 프론트 제작을 포함하지 않는다. 후보 목록과 합치는 책임/계약을 문서화하고 필요하면 작은 수동 검증 예제만 제공한다.
- 동점 정책의 구현 기본값: Redis 조회 순서를 그대로 유지한다(역방향 조회에서는 동일 점수의 member가 역 사전식 순서). 숫자 후보 ID 오름차순으로 보장하지 않는다. 기존 DB 결과 API의 동점 규칙은 유지한다. 이 차이는 사용자 최종 지정 정책이 아니라 순서 유지 결정에서 따른 기본값으로 명시한다.
- 빈 Redis 랭킹은 []이다. 기존 투표가 자동으로 backfill된다고 가정하지 않는다. 이번 테스트는 통제된 새 데이터의 변화량으로 검증한다.

## 4. Redis Pub/Sub 선택 이유 — 사용자 선택 강조
- 모든 SSE 서버가 동일한 변경 알림을 받아야 한다.
- Kafka Consumer Group 방식으로 구성하려면 서버 인스턴스마다 별도 그룹 ID와 소비 시작 위치 등을 고려해야 한다. Redis는 모든 서버가 같은 채널을 구독하는 방식으로 구독 구성을 단순화할 수 있어 선택했다. Kafka 그룹을 수동 생성해야 한다는 의미는 아니다.
- 화면 알림은 과거 변경의 보관·재생이 필수가 아니며 최신 상태를 조회하면 된다. 이 요구가 단순한 구독 구조를 선택할 수 있는 전제다.
- Redis는 이미 랭킹 저장에 사용한다. 다만 Kafka도 이미 있으므로 무조건 더 빠르거나 운영 비용이 낮다는 미측정 주장은 하지 않는다.
- 단일 서버만 보면 직접 SSE 브로드캐스트도 충분하다. Pub/Sub은 여러 서버 각각의 로컬 SSE 연결에 변경을 전달하는 역할이다.
- Pub/Sub은 알림을 보관하지 않는다. 누락 시 다음 알림 또는 SSE 재접속의 최신 조회까지 화면이 오래된 상태일 수 있으며 현재 범위에서 수용한다.

## 5. Pub/Sub 및 SSE 계약
- 집계 true일 때만 live-lunch-choice:ranking-changed 채널에 변경 알림을 명시적으로 발행한다. Redis 점수 변경이 자동으로 알림을 생성하지는 않는다.
- 알림 본문은 추적용 eventId이며 랭킹 전체는 담지 않는다. 각 서버는 알림을 받으면 최신 랭킹을 한 번 조회하고 자신의 SSE 연결들에 전송한다. 주기적 조회나 순위 변동 비교는 하지 않는다.
- SSE 초기 연결/재연결에서도 현재 랭킹을 즉시 보낸다. SSE 이벤트 이름은 ranking, JSON 본문은 랭킹 DTO 배열이다.
- emitter는 서버당 하나가 아니라 SSE HTTP 요청 하나당 하나다. 각 서버의 메모리에 그 서버의 연결만 보관한다.
- remove는 로컬 전송 대상 Set에서 제거하는 것, complete는 비동기 SSE 응답을 종료하는 것이다. 완료/오류/타임아웃 콜백에서 정리하며 중복 remove는 허용한다.
- ConcurrentHashMap.newKeySet으로 연결 목록의 동시 접근을 처리한다. 초기 조회·전송과 브로드캐스트의 순서 역전을 막기 위한 작은 범위의 동기화는 유지한다. 서버 간 잠금이 아니며 느린 전송에 대한 대규모 최적화는 범위 밖이다.
- 예제 타임아웃은 60초다. 전송 주기나 send마다 갱신되는 유휴 타임아웃이 아니다. 브라우저 EventSource 재연결과 초기 전송을 확인한다.
- 집계와 Pub/Sub 발행은 별도 호출이다. 발행 실패 후 중복 이벤트 재시도만으로 알림이 복구된다고 보장하지 않는다. 보상 기능은 이번에 추가하지 않는다.

## 6. 기존 선택 보존
- 익숙한 Spring MVC 계층, Java 명시적 타입, record 응답, YAML 설정을 유지한다.
- 사용자 선택으로 saveAndFlush 유지. 현재 IDENTITY에서 save도 INSERT/ID 확보와 즉시 제약 위반 확인이 가능하며 flush와 commit은 다르다.
- Spring 내부 이벤트와 AFTER_COMMIT 리스너로 DB 커밋 성공 후 Kafka 발행. 처음에는 @Async 없이 진행한다. Kafka ack는 Consumer 처리 성공과 다르다.
- 발행 실패 때 DB 투표를 취소하는 대신 향후 영속 재발행을 검토하는 방향만 유지한다. 이번에 구현하지 않는다.
- 실행 DB는 기존 로컬 PostgreSQL 컨테이너의 전용 DB/유저, 테스트는 격리 H2 및 Testcontainers Redis를 유지한다. 비밀값은 기록하지 않는다.

## 10. 다중 서버 검증 후 구조별 부하 비교 — 사용자 계획
- 현재는 서버 두 인스턴스에서 Pub/Sub이 양쪽 SSE에 전달되는 기능 확인을 먼저 진행한다. 같은 PC에서는 포트를 나누며 독립 인스턴스라는 점이 핵심이다.
- 마지막 단계에서 A(DB 저장·DB 집계·Polling)와 B(DB 저장·Kafka·Redis 집계·Pub/Sub·SSE)를 비교한다. 어느 기술이 무조건 빠르다는 결론을 전제하지 않고 어떤 조건에서 각 구조가 유리하고 비용이 생기는지 설명하는 것이 목적이다.
- 후보 시나리오: 투표 적음/조회 많음, 투표·조회 모두 많음, 짧은 투표 집중. 수치는 아직 정하지 않았고 부하 도구 선택·스크립트 구현·실행은 이번에 하지 않는다.
- 비교 지표 후보: API 처리량·지연·실패율, 최종 집계 정확성, Kafka lag/해소 시간, 양쪽 SSE 최신 상태 도달 및 투표부터 사용자 화면 갱신까지 지연, DB/앱 자원 및 전송량.
- 두 방식 모두 DB에 투표를 저장하므로 Kafka 도입이 DB 쓰기를 제거했다고 해석하지 않는다. Redis는 누적 집계를 읽고, SSE는 변경 기반 전송이지만 잦은 변경에서 전송량이 커질 수 있다.
- 공정한 비교 조건은 후속 설계: 동일 데이터/작업량/서버 수, 자원 예산과 Kafka·Redis 추가 비용 명시, 정상 인덱스를 갖춘 DB 집계, Polling 간격 및 허용 신선도 명시, 반복 측정. 여러 기술을 함께 바꾸는 전체 구조 비교이므로 결과를 특정 기술 하나의 효과로 단정하지 않는다.

## 11. 프로필 분리 → 최소 화면 → 부하 비교 — 사용자 합의
- 동일 코드에서 polling(DB 저장/DB 집계 API)과 realtime(Kafka/Redis/PubSub/SSE)을 선택한다. 공통 로직은 복제하지 않으며 설정은 YAML로 분리한다.
- VoteService의 DB create/results는 공통, Redis rankings/aggregate는 realtime 전용 VoteRealtimeService로 분리한다. 과거 통합 선택은 단순화 목적이었고 이번에는 프로필별 의존성 분리라는 구체적인 필요로 변경한다. VoteResultResponse 통합은 유지한다.
- 커밋 후 Kafka 리스너/Consumer/Redis 접근·구독/SSE Bean은 realtime에서만 등록한다. local과 realtime을 동시에 요구하는 경우 AND 프로필 표현식을 쓴다.
- polling에서도 공통 Spring 내부 이벤트 발행은 유지 가능하나 Kafka 외부 발행은 없어야 한다. 같은 DB로 모드를 바꾸면 polling 시 생성한 투표가 Redis에 자동 반영되지 않음을 기록한다.
- 사용자는 로그/수치뿐 아니라 화면으로 직접 사용하고 싶어 한다. 프로필 분리 뒤 최소 화면(전체 후보, 테스트 사용자 ID, 투표, 득표/순위, 연결 상태)을 붙이고 탭별 갱신을 체험한 뒤 부하 비교로 진행한다.
- 화면은 공유하고 polling 주기 조회/realtime SSE 수신 방식만 구분한다. UI 구현 세부/주기/프레임워크는 아직 결정하지 않았다. 이번 인계는 프로필 분리만 승인한 범위다.
