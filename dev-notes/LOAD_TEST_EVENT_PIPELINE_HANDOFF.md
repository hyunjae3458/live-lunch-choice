# 실제 투표·Kafka 집계·SSE 부하 실험 인계

기록: 2026-10-20 KST. 사용자 요청으로 남아 있는 전체 경로 부하와 실제 투표 이벤트를 통한 Kafka 역할 검증을 CLI에 위임한다. 이번 문서는 실행 지시이며 데스크톱에서 실행한 결과가 아니다.

## 우선 읽기와 현재 상태
AGENTS.md, PROGRESS.md, LOAD_TEST_CAPACITY_RESULT.md의 최신 resume1 부분, LOAD_TEST_CAPACITY_HANDOFF.md, capacity/README.md와 실제 코드/diff를 읽는다. 이 문서가 이전 계획의 실행 순서와 충돌하면 우선한다.
- resume1 조회 진단은 완료된 근거로 보존한다. 100만 표 DB 재집계 병목과 Redis 조회 유지 결과를 Kafka 효과로 해석하지 않는다. 구 polling 결과는 계속 비교 근거에서 제외한다.
- 새 작업은 조회 실험을 재실행하는 것이 아니라 check → full → burst → Kafka 소비 중단/재개 → viewers 순서다. 이전 read 단계의 critical 때문에 full이 자동으로 생략되지 않도록 분리한다.
- 현재 full/viewers 미실행, db-sse와 realtime 소부하 검증 완료. 기존 continue.py는 critical 발생 시 전체 예외 종료되고 경계 반복도 건너뛰므로 아래 범위로 실행 제어를 보완한다.

## 공통 조건과 실행 전 점검
- 제품 코드/사용자 .env/실제8080·5432·9092·6379 자원 보존. capacity 전용 앱/DB/Kafka/Redis만 사용. 새 session/run 이름과 원본 경로로 기록하고 기존 결과 덮어쓰기 금지.
- DB 저장/검증/인덱스/CPU·메모리/JVM·pool 예산, SSE payload/전송정책/900초timeout 동일. A=db-sse 로컬 유한큐, B=realtime Kafka·Redis·PubSub. 양쪽의 전체 구조 비교이며 Kafka 단독 성능 비교가 아니다.
- 초기 시드와 워밍업 기준값을 SQL/Redis로 확인한다. 이전 실험의 진행 중 작업/미소비 이벤트가 새 실험에 섞이지 않도록 전용 자원에서 기존 실행기 초기화 방식을 확인한다. 기존 서비스 토픽 offset/Redis 키 변경 금지.
- 마지막 변경인 사후 CLI 전 자원샘플러 종료를 검증. 지속 AdminClient 사용, 모드 간 계측 조건 동일. CPU throttling/pool 획득 누적시간/queue/lag/send 시간/실패를 기록한다.
- 동일 호스트 자원 경쟁·발생기 지연은 기록한다. 불필요한 사용자 프로세스를 임의로 종료하지 않는다. 발생기 지연/소폭 발생률 미달/SLO 초과는 경고로 유지하고 전체 실험을 바로 종료하지 않는다. 다만 해당 조건을 목표 부하 통과로 둔갑시키지 않는다.
- 변경 범위에 맞는 테스트와 실제 HTTP→Kafka→Redis→SSE 소부하 check를 먼저 수행. seed1만,2관람자,2투표/s 등 기존 check 재사용 가능.

## 1. 지속 투표 부하: 먼저 실행할 주요 실험
- 초기1만 표, SSE100명. 투표10→25→50→100→200req/s. 워밍업30초, 측정180초, drain최대60초. 매 요청 고유userId, 같은 후보 분포/스케줄, 실제 POST /api/votes 사용. readOnly=false 확인.
- 이후 초기100만 표에서 동일 탐색. 낮은 조건부터 시작해 DB 재집계 부담과 후속 큐 적체가 전체 경로에 미치는 영향을 본다. 조회 진단의 실패율을 본 경로 결과 대신 사용하지 않는다.
- 양쪽 A/B 순서를 교차. 조건별 새 기준 상태에서 실행하고 모드별 마지막 통과/최초 실패를 따로 기록한다. 한쪽만 통과한 부하도 보존한다.
- critical(15초 성공응답 없음, 심각한 실패율, OOM, 서비스/호스트 응답 불능 등)은 해당 실행의 신규 부하를 중단한다. 원본과 가능한 종료 상태를 보존하고 실험 앱을 정상화한다. 해당 모드의 더 높은 부하는 진행하지 않는다.
- 한쪽 실패가 다른 모드의 동일 조건 비교까지 영구 차단하지 않도록 한다. 호스트/전용 인프라 회복을 확인한 뒤 상대 모드를 새 상태로 측정한다. 시스템 전체가 회복되지 않으면 억지로 계속하지 않고 미실행 이유를 보고한다.
- 마지막 통과 및 최초 SLO 실패 주변 조건은 탐색 포함 각3회, 정상화 후 재현한다. 시스템 응답 불능을 반복 유발해야 하면 안전하게 재현 가능한 낮은 경계 조건으로 좁히고 심각한 실패 반복을 생략한 이유를 기록한다. 200을 넘는 무제한 증가 금지.

## 2. 짧은 투표 집중과 적체 해소
- full에서 확인한 조건을 사용해 30초 평상 부하 → 15초 증가 부하 → 60초 평상 부하 → 신규 투표 중단 후 최대60초 drain. 평상/증가률은 실행 전에 기록, 200req/s 상한. 가능하면 두 모드가 모두 유지하는 평상률과 후속 처리 적체가 나타나는 안전한 증가률 선택.
- SSE100명,초기1만 표,동일 스케줄로 A/B 각 실행. 양쪽의 API 지연·실패·queue/lag·집계 완료·SSE 관측 지연을 시간축으로 연결한다.
- 적체가 없으면 이 조건에서 여유 있었다고 기록. Kafka의 장점을 보이려고 DB 경로에 sleep을 넣거나 DB 예산/인덱스를 바꾸지 않는다.
- API가 빨라도 lag/집계 지연이 계속 증가하면 지속 처리 용량 통과가 아니다. burst 이후 따라잡으면 그 시간과 최대 적체/최대 갱신 지연을 보고한다. 로컬 큐도 흡수할 수 있으므로 Kafka만 가능한 효과라고 주장하지 않는다.

## 3. Kafka 역할 직접 확인: 실제 투표 중 Consumer 중단/재개
- B 전용 기능 검증으로 별도 실행. 초당5건 이하 또는 앞서 안정적으로 확인한 더 낮은 도착률, SSE2~10명. 초기1만 표. 기존 실험용 stop/start/status를 재사용하며 capacity 전용 격리 환경에서만 활성화한다.
- 정상 처리 확인 → Consumer 정지 완료/할당 상태 확인 →20초 동안 실제 HTTP 투표 → 신규 투표 중단 → 같은 Consumer Group 재시작 → 최대60초 drain.
- 정지 전에 처리 중이던 이벤트는 완료될 수 있으므로 정지 확인 뒤 발생한 eventId를 구분한다. HTTP 성공과 Kafka 발행 ack를 각각 확인. 소비 중에는 Redis/SSE에 미반영된 이벤트가 topic에 쌓이고 재개 후 처리되는지 대조한다.
- DB 저장 건수/성공 ack/토픽 end offset·committed offset/lag/Consumer 집계 eventId/Redis 최종점수/모든 SSE 최종값을 함께 기록. offset commit 시점과 실제 집계 완료는 같다고 가정하지 않는다.
- 이 실험에서 의도한 정지 구간의 지연은 일반 실시간 SLO 통과 판정에서 분리하되 수치를 숨기지 않는다. 소비자 중단 중 접수·브로커 저장·재개 후 처리라는 역할 검증이다. 브로커 중단,프로세스 강제 종료,Outbox/영속 재발행 구현은 이번 범위 밖이다.
- 최종 일치만으로 장애 전반의 exactly-once를 보장하지 않는다. 기존 Lua 멱등성의 범위와 DB 커밋 후 발행 누락 가능성은 그대로다.

## 4. 관람자 증가
- 양쪽에서 검증된 같은 투표률 하나와 초기1만 표를 고정하고100→300→500 SSE 연결. 기존10req/s가 양쪽 통과했을 때만 그대로 사용하고 아니면 공통 통과률을 명시한다.
- 발생기/검증 서버의500연결 한계 이력이 있으므로 사전 용량 검증부터 한다. 발생기 부족이면 서비스 한계로 해석하지 않고 해당 조건 미실행 표시. 별도 호스트가 자동으로 확보되는 것으로 가정하지 않는다.

## 필수 지표와 판정
- 입력: 예정/실제/미발행,실제 도착률,스케줄 지연,in-flight,HTTP 성공/실패/timeout. 실패와 미관측을 분모에서 제거하지 않는다.
- 접수: HTTP p50/p95/p99,SQL 실제 저장/HTTP 불명확 요청의 커밋 여부. DB 저장 성공과 Kafka ack 성공을 별도 집계.
- 후속 처리: Kafka 발행 실패/ack 지연,Consumer 처리율/lag 시계열,eventId별 커밋→집계→브로드캐스트, A큐길이/대기/거절. 모든 모드에 필요한 동일 계측 적용.
- 전달: SSE 수신 p50/p95/p99,누적 목표 미관측 수,전원최종 수렴,연결 오류/재접속,실제 전송량. 누적 목표 관측을 개별 이벤트 처리 완료나 브라우저 렌더링으로 부르지 않는다. 역전/오래된 스냅샷도 기록한다.
- 최종: SQL 기준 후보별 점수와 Redis/클라이언트 일치,이벤트 누락/중복,drain 소요. 샘플링 간격 때문에 정확한 lag0 시각을 모르면 상한/관측 시각으로 표현한다.
- 지속성: 마지막60초 queue/lag/갱신지연 추세. HTTP 성공만으로 통과하지 않는다. 재개된 실험의 원래 SLO는 API p95≤200ms/p99≤500ms,관측 p95≤500ms/p99≤1초,HTTP≥99.9%,발생률≥99%,drain≤60초. 경고로 계속 진행하는 정책과 SLO 통과 판정은 구분한다.
- full의 pass는 현재 도구 flag만 믿지 말고 정확성/발생률/적체추세/계측누락까지 합쳐 확인한다. 수정 도구의 판정 로직과 실행 상태를 함께 검증한다.

## 결과물과 완료 기준
- 새 결과 문서 dev-notes/LOAD_TEST_EVENT_PIPELINE_RESULT.md에 시나리오별 실제 수행 범위/환경/실행명령/원본경로/반복표/경고/중단원인/미실행 범위 기록. 기존 조회 결과는 수정해 새 실험으로 만들지 않는다.
- 접수·집계·전달 지연과queue/lag를 같은 시간축에서 볼 수 있는 표 또는 그래프를 남긴다. 서비스 부하 중 자원과 사후 검증 비용을 분리한다.
- 반드시 세 결론을 나눈다: (1)전체 A/B 구조의 처리 용량 (2)Kafka 소비 분리·이벤트 보관·재개 역할 (3)Redis 사전집계의 기존 조회 효과. DB 쓰기 또는 SSE가 공통 병목이면 그대로 보고하며 Kafka 승리를 전제하지 않는다.
- full 실행을 read critical 뒤에 연결해 생략하지 말 것. 실행 중 critical이 나와도 완료된 조건과 미실행 조건을 분명히 하고 전체 완료라고 쓰지 않는다.
- 작업 후 실험 앱/컨테이너만 정지,원본/DB dump/볼륨 보존. PROGRESS/CLI_HANDOFF/DESIGN_DECISIONS 최신 상태 갱신. 이번 요청은 CLI 실행까지 위임한 것이며 데스크톱 기록 턴에서는 테스트를 실행하지 않았다.
