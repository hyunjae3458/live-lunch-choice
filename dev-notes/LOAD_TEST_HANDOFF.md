# 부하 비교 준비 및 소규모 예비 실행 CLI 인계

## 최신 목적과 범위
- 사용자는 투표 종료/초기화의 서비스 기능 고도화를 하지 않기로 결정했다. OPEN/CLOSING/CLOSED, VotingSession 잠금, eventId DB 저장, 집계 완료 감시, 초기화 API는 설명 단계였으며 이번에 구현하지 않는다. 회고의 미구현 설계 과제로 남긴다.
- 목표: DB+Polling과 DB 저장→Kafka→Redis→Pub/Sub→SSE가 어떤 요청 패턴에서 유리하고 어떤 비용이 생기는지 근거를 얻는다. realtime 우위를 미리 결론내리지 않는다.
- 이번 CLI 요청: 별도 실험 DB와 격리 환경, 재현 가능한 데이터 준비·실행·측정 절차를 만들고 작은 부하로 두 모드의 측정 동작을 검증한다. 대규모 장시간/포화 시험은 예비 결과와 구체적 실행 조건을 먼저 사용자에게 설명한 후 후속으로 진행한다. 제품 UI·후보 변경 SSE·종료/초기화 기능을 선행 추가하지 않는다.

## 기존 상태를 먼저 확인
AGENTS.md, PROGRESS.md, DESIGN_DECISIONS.md, PROFILE_SEPARATION_RESULT.md, 최신 코드/git diff 및 로컬 가용 자원을 읽는다. APP_PROFILE 기본값은 최신 코드에서 확인하고 실험에서는 모드를 명시한다. polling 호출 주기는 현재 화면처럼 응답 완료 후 2초이며 실제 갱신 간격은 응답시간+2초다. 테스트에서 고정 주기로 바꾸면 차이를 기록한다. SSE 연결 타임아웃60초와 재연결도 재현한다.

## 데이터·인프라 격리
- 기존 live_lunch_choice DB에는 실험 데이터를 넣거나 초기화하지 않는다. 기존 PostgreSQL 컨테이너를 재사용해 전용 DB/역할을 만드는 방식부터 검토한다. 예: live_lunch_choice_loadtest_polling, live_lunch_choice_loadtest_realtime. 기존 DB/다른 프로젝트 설정은 변경하지 않는다. 새 전용 컨테이너가 필요하면 이유와 자원 사용을 명시한다.
- 두 DB에 동일 후보·동일 초기 투표 분포를 준비한다. 이름이 겹치는 기존 DB가 있으면 소유·용도를 확인하고 새 DB로 분리하며 덮어쓰지 않는다. 자격 증명은 Git 제외 로컬 설정에만 저장하고 로그/문서에 노출하지 않는다.
- 실험 전용 YAML/환경변수로 접속하며 APP_PROFILE 기본 realtime에 의존하지 않는다. 공통 환경 설정과 polling/realtime의 모드 구분은 유지한다.
- DB만 분리하면 충분하지 않다. Redis 키/채널과 Kafka topic/group도 기존 환경과 섞이지 않아야 한다. 현재 하드코딩 여부를 확인한다. 기본안은 실험 전용 Redis와 Kafka를 별도 로컬 포트로 실행하여 기존 코드 계약을 유지하는 것. 공유 인프라를 쓸 경우 키·채널·토픽·그룹을 모두 별도 설정으로 분리하고 Pub/Sub은 Redis DB 번호만 바꿔도 격리되지 않음을 주의한다.
- 기존 앱을 임의 종료하지 않고 별도 앱 포트를 쓴다. 실행 중 다른 앱/컨테이너와 부하 발생기의 자원 경쟁을 결과에 명시한다.
- 정리 스크립트는 명시적인 실험 DB 이름/전용 컨테이너/실험 접두어만 허용하도록 검사한다. 기존 데이터의 FLUSHALL, 토픽 삭제, offset reset, DB 삭제 금지. 초기화는 테스트 전용 오프라인 준비 스크립트이지 제품 API가 아니다.
- 초기 투표를 DB에 직접 넣으면 realtime Redis에는 자동 반영되지 않는다. 통제된 이벤트 재생이나 전용 시드 작업으로 초기 랭킹/중복 기록을 일관되게 만들고, 부하 전에 DB·Redis의 후보별 기준값을 검증한다. 생성 방식과 준비 비용은 측정 구간과 분리한다.

## 비교 실험 설계
- 처음은 앱1개로 각 모드를 순차 실행. 한 번에 한 변수만 늘린다. 다중 서버와 고부하는 후속 확장.
- 시나리오: (1) 투표 적고 관람자 많음 (2) 투표와 관람자 모두 많음 (3) 짧은 투표 집중. 이번에는 (1)을 작은 규모로 예비 실행한다. 예비 기본값 후보는 관람자10명/투표1건초/30초, 후보4개이며 실제 자원과 사용자당1표 제약을 고려해 확정값을 기록한다. 이는 대규모 성능 결론용 수치가 아니다.
- userId는 실행별 고유 값으로 생성한다. 의도하지 않은 중복409를 처리량으로 세지 않는다. 후보는 관측 구간 중 고정하며 후보 등록 SSE 미구현을 성능 결함으로 해석하지 않는다.
- 동일 후보/초기 데이터 분포/도착 요청률/관람자 수/서버수/앱·DB 자원 설정을 맞춘다. Kafka·Redis 추가 자원 비용도 별도 기록한다. 기본 방식에도 적절한 인덱스를 갖춘 정상 DB 집계를 사용한다.
- polling과 SSE의 JSON(name 포함 여부/0표 처리) 차이 및 전송량 차이를 명시한다. 공통 후보 목록 초기 조회는 동일 조건으로 둔다. 데이터 준비·워밍업·측정·적체 해소를 구분한다.
- 전체 구조 비교에서 여러 요소가 동시에 바뀌므로 측정 차이를 Kafka 단독 또는 Redis 단독 효과로 단정하지 않는다.

## 도구와 지표
- 설치된 도구와 기존 자산을 먼저 확인하고, 실제 SSE 스트림을 읽고 이벤트 시각/재접속을 기록할 수 있는 부하 도구를 선택한다. 일반 HTTP 부하 도구가 SSE 이벤트를 측정한다고 가정하지 않는다. 필요하면 투표 HTTP 부하와 SSE 관측기를 분리하고 시간을 연계한다. 도구 선택 이유와 제한을 설명한다.
- API: 시도/성공/실패 건수, 실제 요청률, 지연 p50/p95/p99, 오류 종류. 응답 성공만으로 realtime 집계 성공을 주장하지 않는다.
- 결과 반영: 요청 시작 또는 응답 완료 중 어떤 시점을 기준으로 했는지 명시하고, polling 응답/SSE 스냅샷에서 상태가 관측된 시각을 기록한다. 현재 SSE는 eventId가 없으므로 동시 투표와 개별 이벤트를 임의로 일대일 대응시키지 않는다. 예비에서는 통제된 투표/후보별 누적 목표치와 최종 수렴 시간을 사용하고 정밀 측정 한계를 명시한다.
- 최종 정확성: 성공한 투표 DB 건수/후보별 변화량과 realtime Redis 결과를 비교. Kafka lag 및 부하 종료 후 해소 시간, 양쪽 모드의 최종 관측 상태 확인.
- 자원: 앱/DB/Kafka/Redis CPU·메모리 및 가능한 DB 쿼리 부하/네트워크량. 가용 지표부터 수집하고 관측 시스템 대규모 구축을 선행하지 않는다.
- 부하 발생기 CPU/연결 한계와 같은 PC 자원 경쟁을 기록한다. 로컬 예비 결과를 실제 대규모 서비스 용량으로 일반화하지 않는다.
