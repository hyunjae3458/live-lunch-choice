# Live Lunch Choice

점심 메뉴 후보를 등록하고 투표하면, 후보별 득표 수와 순위를 확인할 수 있는 학습용 웹 애플리케이션입니다.

Kafka와 Redis를 직접 사용해 보고 싶다는 생각에서 시작했습니다. 화면까지 만들며 실제로 사용할 수 있는 프로그램을 고민했고, 그 과정에서 **기술을 추가했을 때 얻는 이점뿐 아니라 정합성과 운영의 복잡성도 함께 이해하는 것**이 프로젝트의 중요한 목표가 됐습니다.

## 어떤 프로그램인가

사용자는 메뉴 후보를 추가하고, 후보 중 하나에 투표한 뒤 현재 순위를 확인할 수 있습니다.

- 후보 등록과 목록 조회
- 테스트용 사용자 ID를 이용한 투표 등록 및 사용자당 한 표 제한
- 후보별 득표 수와 순위 조회
- 폴링 또는 SSE를 이용한 결과 갱신
- Redis 집계 시 동일 이벤트의 중복 반영 방지
- 다중 애플리케이션 서버에 연결된 SSE 사용자에게 변경 전파
- 실험용 Kafka Consumer 중단·재개 기능

**미구현:** 투표·데이터 초기화, 후보 전체 초기화 기능은 제공하지 않습니다.

프론트엔드는 Spring Boot의 정적 리소스인 HTML·CSS·JavaScript로 구성했습니다. 후보 목록과 랭킹 데이터를 결합해 아직 투표가 없는 후보도 0표로 표시합니다. 실제 로그인·인증, 투표 변경, 여러 투표방 운영은 현재 범위에 포함하지 않습니다. 테스트용 사용자 ID의 중복 제한은 인증이나 부정 투표 방지 기능을 대신하지 않습니다.

## 왜 만들었는가

처음부터 필요한 제품 아이디어가 있었던 것은 아닙니다. Kafka를 제대로 사용해 보고 싶었고, Redis를 단순한 외부 저장소 외에도 Sorted Set, Pub/Sub, Lua 스크립트에 활용해 보고 싶었습니다.

주문 처리처럼 실패와 보상 흐름이 복잡한 프로젝트를 시작하기 전에, 작은 투표 프로그램으로 이벤트가 이동하는 과정을 관찰하기로 했습니다. 후보와 투표라는 단순한 도메인 덕분에 저장, 이벤트 발행, 집계, 화면 전달을 나누어 이해할 수 있었습니다.

학습 질문도 구현하면서 구체화됐습니다.

1. DB 저장과 Kafka 이벤트 발행의 순서를 어떻게 정해야 하는가?
2. Producer의 발행 성공과 Consumer의 처리 성공은 어떻게 다른가?
3. 같은 이벤트를 다시 받아도 집계가 중복되지 않게 하려면 무엇이 필요한가?
4. 여러 서버에 연결된 사용자에게 변경을 어떻게 전달하는가?
5. 기술을 추가한 구조가 단순한 구조보다 유리한 조건은 무엇인가?

## 구현하고 공부하면서 느낀 점

처음에는 Kafka와 Redis를 공부하고 직접 사용해 보고 싶다는 생각으로 시작했습니다. 후보를 만들고 투표를 저장하는 작은 기능에서 출발했지만, 집계와 실시간 전달을 구현하고 화면까지 붙이면서 생각이 달라졌습니다. 단순한 연습을 넘어 실제 생활에서도 사용할 수 있을 만큼 만들어 보고 싶어졌고, 자연스럽게 후보 등록이나 투표 초기화처럼 사용 과정에서 필요한 기능들을 고민하게 됐습니다.

그 과정에서 가장 인상 깊었던 점은, 기능 자체가 단순해도 이를 처리하는 구조가 복잡해지면 고려해야 할 트레이드오프가 크게 늘어난다는 것이었습니다. 특히 투표 초기화를 고민하면서 이를 실감했습니다. DB에서 투표를 삭제하면 끝날 것 같았지만, Kafka에 아직 소비되지 않은 이벤트가 있거나 Consumer가 집계 중이라면 초기화 이후 Redis 점수가 다시 올라갈 수 있었습니다. 새로운 요청을 언제부터 막을지, 이미 받아 둔 요청과 진행 중인 처리는 어떻게 할지까지 생각해야 했습니다.

현재 구조에서 DB 저장, Kafka 발행과 소비, Redis 집계, Pub/Sub 알림은 하나의 트랜잭션으로 묶여 있지 않습니다. 각 단계가 분리되어 있기 때문에 후속 처리를 따로 수행하거나, 소비를 잠시 멈췄다가 다시 처리하는 전략을 마련할 수 있습니다. 하지만 이 분리가 장애를 자동으로 해결해 주는 것은 아니었습니다. DB에는 저장됐는데 이벤트 발행이 실패하면 어떻게 할지, 집계는 됐는데 알림만 전달되지 않으면 어떻게 할지, 다시 처리했을 때 중복 집계가 되지는 않을지처럼 각 경계에서 별도의 판단이 필요했습니다.

처음에는 이벤트가 정상적으로 전달되는 흐름을 이해하는 데 집중했습니다. 구현을 이어 갈수록 “어느 단계까지 성공한 것인가”, “한쪽에서 실패하면 다른 쪽의 상태는 어떻게 되는가”, “재시도하거나 초기화해도 데이터가 맞는가”가 더 중요한 질문이라는 것을 느꼈습니다. 요청과 처리를 분리하면 유입량 변동이나 일부 처리 중단에 대응할 선택지가 생기지만, 그만큼 데이터 정합성과 운영 상태를 이해하고 관리해야 하는 책임도 커졌습니다.

그래서 투표 초기화는 문제를 몰라서 넘긴 기능이 아니라, 필요한 처리 범위를 고민한 뒤 이번 프로젝트에서는 구현하지 않기로 한 기능입니다. 작은 점심 메뉴 투표 프로그램에서 모든 실패와 복구 상황까지 다루는 것은 현재 학습 목적에 비해 범위가 커진다고 판단했습니다. 구현을 계속 추가하는 것뿐 아니라, 어디까지 해결하고 어떤 제약을 남길지 정하는 것도 설계의 일부라는 점을 배웠습니다.

이 경험을 통해 Kafka와 Redis를 사용하는 구조가 항상 더 좋은 구조는 아니라는 생각이 분명해졌습니다. 어떤 제품을 만들고, 얼마나 빠른 갱신이 필요하며, 어떤 데이터를 반드시 보존해야 하고, 어느 정도의 운영 복잡성을 감당할 수 있는지에 따라 같은 구조가 유리할 수도 있고 비효율적일 수도 있습니다. 작은 규모에서는 DB와 SSE만으로 충분할 수 있고, 다른 요구에서는 후속 처리 분리와 사전 집계가 필요한 선택이 될 수 있습니다.

이번 프로젝트에서 얻은 가장 큰 배움은 기술을 연결하는 방법을 넘어, 그 기술이 해결하는 문제와 새로 만드는 문제를 함께 보는 관점입니다. 앞으로는 사용해 보고 싶은 기술이 있다는 이유만으로 구조를 결정하기보다, 제품에 필요한 보장과 허용할 수 있는 제약을 먼저 정하고 그에 맞는 구성을 선택하고 싶습니다.
